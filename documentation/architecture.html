Architecture

Un seul projet Flutter sert quatre plateformes ; un seul backend Firebase les sert toutes. Entre les deux, une règle qui explique la moitié des choix de ce dépôt : la clé Gemini ne descend jamais jusqu'au client.

Le principe

Kass'Dalle est un livre de cuisine familial : on y importe des recettes depuis des photos ou des PDF, on les corrige, on les valide, on les cherche, on les planifie. L'IA intervient partout — mais toujours depuis le backend.

Le client Flutter parle à Firebase avec les SDK officiels : Auth pour l'identité, Firestore pour les données, Storage pour les fichiers. Chaque fois qu'un appel d'IA est nécessaire — Gemini, Claude ou Cloud Vision —, il passe par une Cloud Function HTTPS callable ou par le pipeline asynchrone. Aucune clé d'API n'est embarquée dans le binaire, ni dans le bundle web.

Conséquence directe : le client ne sait pas parler à Gemini. GeminiService côté Dart est un pur client d'appels callable ; sa méthode extractRecipes lève délibérément une UnsupportedError pour empêcher tout retour en arrière.

Vue d'ensemble

Deux chemins mènent à Gemini : le chemin synchrone, pour tout ce qui doit répondre en quelques secondes, et le chemin asynchrone, pour l'import de documents qui peut prendre plusieurs minutes.

Le pipeline d'import

Importer une page de livre demande deux à cinq appels d'IA et le découpage d'images : trop long pour un appel synchrone. Le client dépose un document dans processing_jobs/ et n'attend rien ; le reste se passe côté serveur.

Trois détails valent d'être connus avant de toucher à ce code.

L'étape image_decode existe dans STEP_ORDER mais n'est jamais empruntée : le décodage se fait à l'intérieur de l'étape design. La constante est conservée pour ne pas décaler les index des jobs déjà enregistrés. L'étape design a deux chemins, selon la case « Extraire les illustrations » cochée à l'import et portée par le job. Décochée : un appel de pré-contrôle par page, qui compte les photographies sans rien extraire — le détecteur complet servait ici, et l'appelant n'en gardait qu'un entier. Cochée : la chaîne complète de illustrations/extract.ts — pré-contrôle, cadrage, mise à plat, remise à l'endroit, zones, découpe — détaillée dans les diagrammes de séquence, séquence 12. Les deux ne se cumulent jamais : le pré-contrôle pose exactement la question de la détection seule. Les illustrations sont best-effort. Une détection qui échoue est journalisée via logError puis ignorée : la recette est créée sans image plutôt que pas du tout. Même politique pour la génération de vignettes WebP et la suggestion de tags. La détection tourne sur chaque page du scan et non sur la première seule — le texte d'un import multi-pages était lu en entier, ses photographies ne l'étaient pas. Chaque page coûte une détection. Les boîtes viennent d'un modèle, pas d'un détecteur géométrique : trois filtres locaux et gratuits écartent avant toute publication ce qui n'est manifestement pas une photographie — trop petit, bande plutôt qu'image, ou presque blanc et sans couleur, c'est-à-dire du papier. Ils sont conservateurs par construction : jeter une vraie photo est irrattrapable, garder une découpe douteuse ne coûte qu'un rejet de plus à la modération. Une image ne se publie jamais depuis le client. Les quatre portes qui en publiaient une — book_cover, recipe_illustration, draft_illustration, free_recipe_cover — passent toutes par quarantine/ puis par moderateAndPromoteImagesFn. Le cœur de la modération vit dans moderation/moderateAndPromote.ts. Les dossiers publiés sont fermés en écriture côté Storage : c'est ce qui rend la modération incontournable plutôt que polie. Une image produite par l'IA ou livrée avec l'application emprunte le même chemin sans être analysée — son origine est inscrite au journal, ce qui dit pourquoi elle est passée. Les découpes du serveur, elles, s'écrivent en direct. Le fichier source est déjà passé par le scan de sécurité à l'envoi, et une découpe est un JPEG que Sharp vient d'encoder : en vérifier le format reviendrait à vérifier notre propre encodeur. L'analyse Cloud Vision porterait sur un morceau d'une photo que le compte a lui-même envoyée, et elle est facturée à l'image. Les visuels produits par l'IA écrivent déjà au même endroit, de la même façon. Sur la dernière tentative, le job bascule en dead_letters/ et la fonction retourne normalement — elle ne relance pas d'exception, sans quoi Cloud Tasks recommencerait indéfiniment. La reprise se fait à la main depuis Admin → File d'échecs.

La surface Cloud Functions

Quarante-neuf fonctions déployées, toutes exportées depuis functions/src/index.ts. La garde d'accès est explicite dans chacune : requireAuth, requireEditor ou requireAdmin, depuis callable/_auth.ts. Trois entrées existent dans le code sans être déployées, faute d'appelant — extractBookCoverFn (l'extraction se fait dans le pipeline), consolidateShoppingListFn (dans onRecipeWritten) et normalizeNutrientsFn (reprise ponctuelle). Elles ne figurent pas ici : une fonction non exportée depuis index.ts n'existe pas en ligne.

La logique dupliquée Dart ↔ TypeScript

Quatre logiques métier existent en double — parseur CookLang, parsing de quantité, conversion d'unités en grammes, identité d'un ingrédient —, plus deux résidus : l'arithmétique de la grille tarifaire et deux seuils d'hygiène du planning. Le client en a besoin pour afficher sans aller-retour, le backend pour calculer.

Deux fixtures sont serveur seul : les règles de créneau du planning et le verdict de modération d'une image. Elles disent l'inverse d'une duplication — la logique n'a pas de jumeau côté client, et la fixture n'existe que pour verrouiller la version serveur. Les prix, eux, ont quitté le code pour Firestore : ce qui reste en double n'est plus que du calcul appliqué à une table reçue en argument.

Les fichiers kass_dalle/test-fixtures/*.json sont rejoués par les deux suites de tests — test/*_test.dart et functions/src/tests/. Corriger un bug d'un seul côté fait échouer la CI de l'autre. Ajoutez le cas dans la fixture avant de corriger.

Les écarts assumés vivent dans la section divergences de unit_to_grams.json. Les réduire est un objectif ; les ignorer n'en est pas un.
