Architecture

Un seul projet Flutter sert quatre plateformes ; un seul backend Firebase les sert toutes. Entre les deux, une règle qui explique la moitié des choix de ce dépôt : la clé Gemini ne descend jamais jusqu'au client.

Le principe

Kass'Dalle est un livre de cuisine familial : on y importe des recettes depuis des photos ou des PDF, on les corrige, on les valide, on les cherche, on les planifie. L'IA intervient partout — mais toujours depuis le backend.

Le client Flutter parle à Firebase avec les SDK officiels : Auth pour l'identité, Firestore pour les données, Storage pour les fichiers. Chaque fois qu'un appel Gemini est nécessaire, il passe par une Cloud Function HTTPS callable ou par le pipeline asynchrone. Aucune clé d'API n'est embarquée dans le binaire, ni dans le bundle web.

Conséquence directe : le client ne sait pas parler à Gemini. GeminiService côté Dart est un pur client d'appels callable ; sa méthode extractRecipes lève délibérément une UnsupportedError pour empêcher tout retour en arrière.

Vue d'ensemble

Deux chemins mènent à Gemini : le chemin synchrone, pour tout ce qui doit répondre en quelques secondes, et le chemin asynchrone, pour l'import de documents qui peut prendre plusieurs minutes.

Le pipeline d'import

Importer une page de livre demande deux à cinq appels Gemini et le découpage d'images : trop long pour un appel synchrone. Le client dépose un document dans processing_jobs/ et n'attend rien ; le reste se passe côté serveur.

Trois détails valent d'être connus avant de toucher à ce code.

L'étape image_decode existe dans STEP_ORDER mais n'est jamais empruntée : le décodage se fait à l'intérieur de l'étape design. La constante est conservée pour ne pas décaler les index des jobs déjà enregistrés. Les illustrations sont best-effort. Une détection qui échoue est journalisée via logError puis ignorée : la recette est créée sans image plutôt que pas du tout. Même politique pour la génération de vignettes WebP et la suggestion de tags. Sur la dernière tentative, le job bascule en dead_letters/ et la fonction retourne normalement — elle ne relance pas d'exception, sans quoi Cloud Tasks recommencerait indéfiniment. La reprise se fait à la main depuis Admin → File d'échecs.

requireAdmin et requireEditor lisent users/{uid} dans Firestore à chaque appel — rôle et révocation. requireAuth, lui, tranche sur le claim role du jeton et ne lit le document que si le jeton n'en porte pas : un compte pending ou révoqué ne doit pas atteindre une entrée qui dépense. Les Security Rules s'appuient sur les mêmes custom claims, alimentés par syncUserClaims, avec repli sur le document. Les deux mécanismes coexistent : changer un rôle prend effet immédiatement côté callable et côté Firestore, mais seulement au rafraîchissement du jeton côté Storage.

La logique dupliquée Dart ↔ TypeScript

Trois logiques métier existent en double : le parseur CookLang, le parsing de quantité, la conversion d'unités en grammes. Le client en a besoin pour afficher sans aller-retour, le backend pour calculer.

Les fichiers kass_dalle/test-fixtures/*.json sont rejoués par les deux suites de tests — test/*_test.dart et functions/src/tests/. Corriger un bug d'un seul côté fait échouer la CI de l'autre. Ajoutez le cas dans la fixture avant de corriger.

Les écarts assumés vivent dans la section divergences de unit_to_grams.json. Les réduire est un objectif ; les ignorer n'en est pas un.
